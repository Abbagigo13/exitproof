# Security

## Threat Model

DeFi Risk Intelligence Platform is a read-heavy client-side application with two state-mutating onchain operations: anchoring a receipt hash and paying 1 USDC for premium access. The attack surface is narrow but real.

| Actor | Capability | Risk Level |
|---|---|---|
| Passive user | Read risk data, compute hashes | None |
| Active user (wallet connected) | Anchor receipts, pay USDC | Low |
| Malicious webpage (XSS) | Steal localStorage, trigger wallet popups | Medium |
| Malicious receipt URL | Inject crafted snapshot data | Low |
| Compromised DefiLlama API | Serve manipulated protocol data | Medium |

## Smart Contract Security

### RiskReceiptRegistry

The contract was audited at deploy time (see the security review findings in AGENTS.md). Key properties:

- **One receipt per hash**: `anchorReceipt` reverts if the hash already exists. This prevents overwriting or spoofing an anchored receipt.
- **Permissionless anchoring**: any address can anchor any hash. This is intentional — the registry is a notary, not an access-controlled store. The anchorer address is recorded so verifiers can judge trustworthiness.
- **No fund custody**: the contract holds no ETH or tokens. The only economic activity is gas for anchoring.
- **Ownable but inert**: the `owner` can call `renounceOwnership` / `transferOwnership` but has no privileged anchoring or reading capability. The owner role exists only as a future extension point.
- **No upgradability**: the contract is not upgradeable. A new version requires a new deployment and a UI config update.

### Premium Payment

- The 1 USDC transfer goes to a fixed treasury address (`0x5B12Ce46C7194aD57d143bC22847224047b1Ef42`) stored in `src/lib/registry.ts`
- The UI does NOT verify the on-chain payment before unlocking — it trusts the `useWaitForTransactionReceipt` confirmation. A determined user could call `approve` then `transferFrom` from another path and skip the UI. This is acceptable for a testnet product; a mainnet version must verify the Transfer event on-chain before lifting the gate.
- `localStorage` keys are `premium:<address>:<protocolId>` — scoped to wallet address and protocol. Clearing localStorage resets access but does not charge the user again (the on-chain transfer already happened).

## Frontend Security

### Input Validation

- **Receipt URL param (`?receipt=`)**: the base64 payload is decoded and parsed with `JSON.parse` inside a `try/catch`. Malformed input renders the fallback "invalid receipt" state. Fields are accessed with optional chaining and rendered as text (not `dangerouslySetInnerHTML`), preventing XSS via crafted receipt payloads.
- **Hash input in VerifyPanel**: accepts free-form text, normalises to lowercase, validates the `0x` prefix and 64 hex chars before calling the contract. Invalid input shows an inline error — no contract call is made.
- **DefiLlama response**: typed through `as unknown as DefiLlamaProtocol[]` then validated field-by-field in the mapper. Missing or wrong-type fields fall back to safe defaults. No field is used as HTML.

### Content Security

- No `dangerouslySetInnerHTML` anywhere in the codebase.
- Protocol names, descriptions, and categories from DefiLlama are rendered as React text nodes — React escapes them automatically.
- Receipt snapshot data from URL params is treated as untrusted data, not instructions.

### Wallet Interaction

- ConnectKit handles the connection modal. No private keys are accessed or stored by the application.
- Transaction calls go through wagmi `useWriteContract` — the user's wallet extension (MetaMask, etc.) presents the confirmation screen. The app cannot bypass wallet confirmation.
- The app never asks the user to sign arbitrary messages that could be replayed as transactions.

### localStorage

- Premium access flags in `localStorage` are low-value (they gate a testnet paywall). Clearing them is non-destructive — the user just needs to pay again.
- No sensitive data (private keys, API keys, personal information) is stored in `localStorage`.

## Dependency Security

- All dependencies are pinned in `bun.lock`. Run `bun audit` periodically to check for known vulnerabilities.
- The largest attack surface is wagmi + viem (maintained by Wevm with a strong security track record) and ConnectKit (Family).
- DefiLlama is fetched over HTTPS. The app renders data from it as plain text only — a compromised response cannot execute code.

## Mainnet Considerations

Before deploying on mainnet or charging real USDC:

1. **Re-audit the contract** with a professional firm — the current audit is a development-time review, not a formal engagement.
2. **Verify premium payments on-chain**: query the `Transfer` event from the USDC contract to confirm the payment before unlocking premium content. Do not rely solely on `useWaitForTransactionReceipt`.
3. **Add a server-side receipt verification endpoint**: the current share URL encodes receipt data in the URL, which is tamper-evident (the SHA-256 hash) but not tamper-proof in the UI display layer. A server endpoint that re-derives the hash and compares it to the on-chain anchor is needed for a trust-minimised verifier.
4. **Rate-limit anchoring**: consider a per-address cooldown in the contract to prevent spam anchoring that pollutes the registry.
5. **Review the treasury address**: the current treasury is the Circle platform deployer wallet. Use a multisig (e.g. Safe) on mainnet.
